Dear all,

I'm new here, so first of all I'd like to thank the developers for all
the hard work they've put into Maxima!

I'd also like to propose a contribution in return. I've ported Sympy's
code for denesting square roots to Maxima. I hope it turns out to be
useful. (see attachments)

Since it's my first Maxima package I'm not so sure either that I'm
always using the most appropriate functions, that I'm handling the local
and global variables (e.g. domain...) as I should, etc.
Any feedback will be appreciated.

Most of the code is a rather direct port of Sympy's functionality, but
there are some extensions to it that apply to cube roots or n-th roots.
There's also an extensive test suite. (BTW, for two problems maxima
detects an erroneous result when in fact the shown result is identical
to the expected one!? That's with maxima 5.37.2.)

The main algorithms are those of Borodin et al.: "Decreasing the Nesting
Depth of Expressions Involving Square Roots"
http://researcher.watson.ibm.com/researcher/files/us-fagin/symb85.pdf

Other references are in the code comments.

I'm aware that there are more general approaches (e.g. by Landau,
Blömer) but I haven't tried (yet?) to implement those.

Below you'll find the output of the included demo file.

Kind regards,

Gilles Schintgen

> The code   if subst(s,x,eq)  then .... 
> looks very suspicious;  rat(float (...))  also looks suspicious.
> setting ratepsilon to 2e-10 -- why?

You're right about that part looking suspicious and I kind of agree. At
the very least I should probably determine the rational roots of the
polynomial first and then check (to a much higher precision) if one of
them is numerically equal to the radical sum 's'.

Still, this is the fundamental weakness of the approach outlined in
Osler's article (or I misread it...): a denesting provably exists if
there's a rational root of a specific polynomial that equals the sum of
the given radical expression and its "conjugate". But since that sum is
by definition a sum of two nested radicals, this check is problematic in
that it involves the radical we're trying to denest... Hence the
numerics. (If I remember correctly those polynomials can have multiple
rational roots, so the check with the radical sum is necessary.)

The current code takes quite a shortcut in that it determines a
"plausible" rational approximation of s and then checks (symbolically)
that this rational is in fact an exact root of the polynomial.

In some way it's an elaborate heuristic. (This includes the rather large
ratepsilon without which rat fails to "identify" even some of the
simplest rationals.)

> There  is also a function sqrtdenest()  which does some things.

Yes and I'm rather confident that raddenest can denest all the
expressions that sqrtdenest denests. (This specifically includes the
case where a fourth root is first denested to a square root which then
denests again.)


> I hope that the root structure for the denested radicals is the same ..
> for example,   sqrt(2) +sqrt(3)   has 4 values, because sqrt(2) is
> +-,    and so is sqrt(3).

I wouldn't bet on it, most of the algorithms assume the real-branch
definitions/interpretations of the various radical expressions. (Just as
maxima: sign(sqrt(2)) returns pos and not pn.)
In some parts I tried to be as coherent to maxima's conventions as
possible, especially regarding the domain variable.

Without looking at the translation of _sqrtdenest1, my first guess is
that problem is that code for conditional expressions is translated
incorrectly. Here's a prototypical case which is similar to
_sqrtdenest1.

(%i7) g(x) := block(if x > 0 then return(1), 0) $
(%i8) [g(1), g(-1), g(u)];
(%o8)                              [1, 0, 0]
(%i9) translate(g) $
(%i10) [g(1), g(-1), g(u)];
(%o10)                             [1, 0, 1]

Note that the g(u) has changed from 0 to 1.

The problem is that the generated code assumes that Boolean expressions
evaluate to true or false. I think there's a bug report about this
already. You can see if non-true-or-false comes into play by setting
prederror:true and then try the example again.

The basic algorithm in this game for denesting sqrt(a+b*sqrt(r)) 
consists in computing a^2-r*b^2, see if it is a square and apply
simple identities. However when the initial quantity depends on several
independent square roots, say sqrt(2), sqrt(3), sqrt(5), etc. then
a, b above already contain radicals. In this case it may well be that 
the supposedly denested formula is more complicated than the initial 
one. So people try different strategies, recursively, and you need some
heuristic to stop the expenses somewhere. Computing the length of the 
string produced appears to be one of such heuristics.

Have a look at the algorithm, apparently used by Maple,  in Section 4.7 
of Jeffrey, David J. and Rich, Albert D. (1999) Simplifying Square Roots 
of Square Roots by Denesting, in Computer Algebra Systems (Ed. M. J. 
Wester) <http://www.cybertester.com/data/denest.pdf>

You are correct in saying a measure of expression complexity - other 
than the maximum degree of nesting - is required to prevent 
flip-flopping between expressions of equal depth.  An example is 
sqrt(sqrt(2)+1) => sqrt(1/sqrt(2)+1/2)+sqrt(1/sqrt(2)-1/2) => 
sqrt(sqrt(2)+1)

;;; A measure N(e) to control the recursive denesting of radicals in e
;;; Ref: Jeffrey and Rich (1999), section 4.7
;;;
;;; 1) A number x:            N(x) = 1                     (4.7.1)
;;; 2) The n-th root x^(m/n): N(x^(m.n)) = 1 + N(x)        (4.7.2)
;;; 3) A product x*y:         N(x*y) = max(N(x)*N(y))      (4.7.3)
;;; 4) A product x+y:         N(x+y) = N(x) + N(y)         (4.7.4)
;;;
;;; Rule (4) for sums gives a bonus for reducing the number of terms.
;;; e.g it rewards the transformation
;;;    sqrt(2)+sqrt(8) => 3*sqrt(2)
;;; and discourages
;;;    sqrt(sqrt(2)+1) => sqrt(1/sqrt(2)+1/2)+sqrt(1/sqrt(2)-1/2)
;;;
;;; Example: sqrt(3+2*sqrt(2)) = 1+sqrt(2)
;;; N(sqrt(3+2*sqrt(2))) = 1+N(3+2*sqrt(2)) = 1+N(3)+N(sqrt(2)) = 4
;;; N(1+sqrt(2)) = 1 + N(sqrt(2)) = 3
;;; therefore prefer rhs to lhs.

For now I have replaced string-length (which was an ugly kludge anyway)
by N(e) and am happy to report that there's not a single change in the
testsuite results. :-)

As for a direct comparison of trees I'm not sure that in this case
there's an obvious pecking order among operators. After all it's the
nesting that's most significant. (On the other hand if it's only used as
a secondary check, the absolute nesting depth is already taken care of.)
The one thing that's now slightly bothering me is that first absolute
nesting depth is compared and then an almost identical tree traversal is
done if the first check reports equality. Still, string length is out
and that's definitely an improvement.

I'll see how often it comes to this second check for the examples in the
testsuite. It's quite possible that there are not that many calls to
